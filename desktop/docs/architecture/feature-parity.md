# Paseo feature inventory and Rust rebuild parity plan

Status: first-pass architecture/design inventory, not an implementation claim. **Observed** means verified from the installed Paseo 0.13.0 CLI help, local configuration or persisted files; **proposed** means a Rust-rebuild target or acceptance test. No mutation of the existing Paseo home or Talos repository is assumed. Some capabilities are exposed by help/config but were not exercised end-to-end; these are explicitly marked **surface-only**. The CLI package at `~/.local/lib/node_modules/@getpaseo/cli` and the installed `~/.local/opt/Paseo.AppImage` establish the installed distribution; desktop interaction, network services and permission prompts were not tested.

## Rust implementation tracking and sequencing

This inventory defines requirements, not current implementation completion.
[../STATUS.md](../STATUS.md) maps every area below to source/test evidence,
remaining acceptance and a backend-first execution phase. The active sequence is
P0 baseline → P1 daemon/CLI vertical slice → P2 local backend parity → P3 migration
and distribution → **P4 desktop UI last**. Existing UI work is preserved but its
expansion and QA are deferred until the non-UI gates pass. M3 capabilities remain
a separate post-local-release backlog; no parity row is silently dropped.

The MVP priorities below describe release scope, not permission to implement UI
in parallel with the backend. Final release still requires both CLI and desktop
acceptance and full-workspace checks; fixture-only results are not live acceptance.

## Scope and priority

**MVP** means usable local coding-agent workflow with safe preservation of existing data. **Post-MVP** means a separate delivery milestone, not permission to silently drop existing behavior. Preserve extensible domain/API types for deferred features. For every command below, CLI help establishes a public surface, not proof that a particular provider, desktop OS, or remote service currently works. Compatibility means equivalent user-visible semantics, not byte-for-byte internal implementation.

## Existing-data migration contract (MVP)

**Observed:** `~/.paseo` contains `config.json`, `projects/{projects,workspaces}.json`, `agents/<cwd-derived directory>/<id>.json`, `creations/*.{json,claim}`, `agent-requests/*`, `desktop-attachments/*`, `worktrees/*`, plugin directories/settings/cache, `models/local-speech/*`, `runtime/opencode/*`, schedules directory, identity/credential/token files and a PID file. Desktop data also lives under `~/.config/Paseo`. This is an observed inventory, not an assertion that every file is portable or safe to rewrite. Some data contains secrets and private prompts; this report intentionally omits their values.

**Proposed:** default to a new Rust-owned data directory; import via read-only scan and dry-run summary, snapshot/backup, then transactional copy/convert with schema/version markers and an import journal. Preserve stable project/workspace/agent IDs, archives, workspace ownership flags, relationships, labels, statuses and historical timeline references; copy referenced attachments with hashes and verify integrity. Treat credentials/push tokens, process IDs, runtime sockets, stale claims, provider runtime files, model caches, plugin binaries and desktop IndexedDB as separate opt-in or regeneration classes, **not** blindly executable/importable. Do not delete or modify `~/.paseo`, its worktrees, or original repository checkouts during import. Deduplicate reruns by original ID/source fingerprint, report unrecognized fields without discarding their recoverable payload, and allow rollback by discarding only new Rust-owned outputs. Import tests: fixtures covering git/non-git and archived workspaces, managed/unmanaged worktrees, concurrent agents, pending permissions, missing/corrupt JSON, broken attachment references and a partial interrupted import; verify source hashes unchanged, stable IDs, deterministic rerun and redacted diagnostics. Provider sessions may require adapter-specific reconciliation; where replay cannot be recovered, mark historical/read-only rather than implying the agent is live.

## Release gate

MVP is done only when a fresh install and a dry-run migration both succeed; local project → workspace → provider agent → streamed follow-up → permission decision → interruption/restart → archived history works from CLI and the chosen UI; two agents remain isolated; persisted state survives restart; and tests establish that neither source Paseo data nor unmanaged worktrees are modified. Post-MVP checklists above are explicit outstanding parity debt until each is independently exercised against the installed product and accepted. This inventory is **not** a claim that parity has already been delivered.
